## Summary

Both repos are in good shape for a week-old, agent-built project: the code is small, stdlib-only where it can be, fail-closed where it matters, and well tested where tests can run; the job pipeline is real (158 merges in 7 days, every cited run id resolves, reviewers find bugs with repros), and most of Empire's PC lessons became defaults with Windows integration tests. The gates, though, enforce the honest case and not the adversarial or the unlucky one: every enforcement point reads its rules from the branch it judges, a red `main` after a merge is never re-run or reported, the build id can name two different DLLs, and the 20-pass acceptance evidence is checked for existence rather than authenticity. The lessons Empire paid most for (look at the pictures, usage accounting, approval is not a default flip) are still prose, and two have already recurred.

Findings by severity across the five reviews: 1 blocker, 16 high, 44 medium, 28 low (89 as filed, about 85 distinct since four were found by two reviewers; the sections below carry the ones that change a decision, the reviewers' full reports are listed in the appendix).

The three changes that matter most:

1. **Make `main` honest (S).** Rerun a slow CI set on `main` when its last run there failed, tell someone, and print a red `main` from `jobs next`. Today Napoleon's `proxy` build has been red or unknown since J24 merged (run 41664906781) and the core's was red at v0.16.0 (run 41716930333; three later tags changed proxy inputs, so check its latest main run); nobody was told because `notify` excludes `main` and later pushes skip the set as unchanged. Open the two run logs: the cause lies outside the hashed inputs (likely the unpinned mingw or the lua.org download).
2. **Judge a branch with the base's rules (M).** Policy, `wsc.toml` `[policy]`, the hook modules and the `core` gitlink all come from the head today, so one edit switches any rule off (reproduced four ways); `meta/` can move the pin and 57 DLL inputs with zero acceptance passes. This is the fix every later automation (agent-merged `plan/`, auto pin bumps) depends on.
3. **Close the release gaps before 0.1.0 ships (M).** The shipped crash-dump tool cannot run outside the repo, the D46 gate runs before component keys are merged so the dev side is on in the release DLL, the DLL check is a substring match that accepts `-dirty`, and the installer and its 11 tests have never run in CI. J24 also merged three shadow keys as release defaults that its own report leaves to you.

On automation: tagging the core, pin bumps, narrow `plan/` merges and the batch "as recommended" answers are chores an agent can own with the guards in the Automation section; taste, scope, release values, licences and publishing stay yours and belong on one lane of the status page.

## Pipeline and gates

The gates enforce most of what the docs claim, but every enforcement point reads its rules from the branch it is judging, and a red `main` after a merge is never re-run and never reported. Those two facts explain the serious findings below; the rest is detail.

**P1 (blocker): a red required check on `main` is permanent and silent.** Pass markers are `actions/cache` entries keyed on a content hash of the input set (`warscape/ci.py:``71-84, ci_render.py:47, 86-92, 117`), saved only on push runs and scoped per branch. On `job/J24` an earlier push built the DLL and saved the marker; the head commit `61f679b` changed no proxy input, reused it, and showed `proxy=SKIPPED`; auto-merge counts skipped as green. The squash `cbf3105` is a new tree in `main`'s scope, so `proxy` ran there and failed (run 41664906781). Every later push to `main` diffs against the previous `main` tip, sees no proxy change and skips without looking for a marker. `notify` has `github.ref != 'refs/heads/main'` (`ci_render.py, the notify job's if:`) and `jobs next|review|view` read open pull requests only (`jobq.py:365`), so nobody is told. The DLL build id at `cbf3105` is `75739186b92e`, the build J24's 20 PC passes ran on, so the cause lies outside the hashed inputs (runner image, unpinned apt packages, the lua.org download, host tests, or a flake); the logs need your sign-in. The same `thing happened on the core: proxy failed on main at v0.16.0 (run 41716930333) after passing on the branch head 28f7de6; v0.17.0 to v0.18.0 changed proxy inputs since, so the core's current state needs a look at its latest main run`. Fix (S-M): on a push to `main`, run a set whenever no marker exists for its tree in `main`'s scope; give `notify` a `main` branch; have `jobs next` print a red `main` first.

**P2 (high): a branch can switch any rule off.** `policy.run_check` loads `wsc.toml` `[policy]` and the hook modules from the head checkout (`warscape/policy.py:194-217`; CI runs `python wsc.py policy` on the head, `policy.yml:32`). Reproduced four times in a scratch clone: `bootstrap=["foo"]` passes a code change on a `foo` branch; `session_trailer=""` passes a self-reviewed job; a `policy.check` that returns `[]` passes anything; `decisions=""` ends append-only. A Napoleon `job/` branch may also repoint the `core` gitlink at any pushed commit, and CI then runs that commit's policy. Rule 79 is the one check already judged with the base's code (`jobs_hooks.py:263-276`); the rest should follow it. Fix (M): judge the head's diff with the base's `warscape/`, `[policy]`, `[jobs]` and hooks, or refuse any change to those outside `meta/`.

**P3 (high): `meta/` is an escape hatch.** Napoleon's meta globs match 533 of 5,723 tracked files, including `core`, `registries/*` (fnmatch `*` crosses `/`, so `registries/engine_sites.jsonl` and every job row), `tools/jobs_hooks.py` and `tools/claude_hook.py`; rule 79 runs only when `kind == 'job'` (`tools/jobs_hooks.py:351`). A pin bump as `meta/` moves 57 proxy and harness files with zero acceptance passes, and "meta waits for Liam" has no guard (P6). Fix (S): rule 79 for every branch kind; drop `core` and `registries/*` from meta; use the segment-aware matcher the gates already use.

**P4 (high): after the pin bump, CI's proxy input set misses a DLL input.** Core 0.16 hashes `viewer/pins.json` and `fetch_ui.py` into the build id (`proxy/tools/build_id.py:31-36`); Napoleon's `[ci.inputs] proxy` regex has no `^viewer/`. A pins change would rebuild the DLL and fire rule 79 while CI skips the job. Fix (S): derive the set from `build_id.INPUTS`, or a gate that every build-id input path matches the regex.

**P5 (high): the v0.9.0 to v0.16.0 bump is a PC job, not a commit.** Tested against core main: every verb refuses to load (`verb 'discovery' already exists`, `cli.py:28`); `proxy/napoleon/adapter.cpp:63` needs the new `gesture` member; the build id changes so rule 79 needs 20 passes; the Napoleon `proxy` CI timeout (15 min, `ci/gates.yml.in:75`) is below the 30 min the core needed once RmlUi compiled.

## warscape-core code quality

The core is good code with a credibility gap: the pure logic is small, tested and fail-closed, while the claims the pipeline rests on (a build id that names one DLL, 20 acceptance passes that prove it, guards that stop an agent) are each one step short of true. Numbers: core 240 unit tests plus 109 host tests pass; the proxy's 16 host-test suites (about 3,400 checks on Napoleon's tables) pass and 60 parallel reruns showed no flakes; `build.sh repro` reproduces the DLL byte-for-byte from another path; the watcher has 29 Windows integration cases that run the real script against fake games.

**Python (CLI, gates, policy, job queue).** Small, stdlib-only, Python 3.12, with error messages that say how to fix things, a real closed-subset JSON Schema validator (`warscape/schema.py`), one readiness rule shared by the CLI, page, server and autopilot, and one-file-per-row registries with reversible Windows-safe names. The defects are the enforcement model of the previous section (P1 to P3) plus: the hook module in Napoleon re-implements `policy.show` and reads job rows by path against CONSUMING.md's own rule (`tools/jobs_hooks.py:105-109, 213-231`); `gen_tables.py:177` reads `registries/engine_sites.jsonl` by path, so a `reg migrate --to dir` would break the generator and drop it out of the CI input regex; `tests/test_jobs_hooks.py:303` greps for a source line instead of testing behaviour; `[gates] skip` hides gates without a word.

**Proxy DLL (C++) and tools.** One pass-through switch (`guard.h PlanEngine`) that every engine-side module asks, an all-or-nothing patch plan with relocation-aware compares, reproducible build flags, a crash handler that cannot make a stack overflow worse, and a vtable chain registry that prevents Empire's double-hook trap by construction. ## Automation opportunities

You touch the pipeline in about 18 ways today; roughly 7 are genuine taste, scope, risk or legal calls and the rest are chores an agent can own once a guard exists. The three with the best return are the core release tag, the pin-bump job, and narrow `plan/` merges, in that order, and two of them depend on fixing P2 first.

**1. Core release tag (M).** Every tag today sits on a first-parent `main` commit whose PR bumped `VERSION`, so the tag is already a pure function of the merge. Design: a `semver` field on the W-job row (`patch|minor|major|none`, checked by the brief hook) replaces editing `VERSION` on job branches and ends the renumbering race that lost v0.11.0 and v0.12.0; a workflow on push to `main` computes the next version from `done` rows since the last tag, waits for every required check on that commit to be green (P1 shows `main` can be red, and v0.16.0 was tagged on a red `proxy`), commits `VERSION` on a new `release/` branch kind that policy limits to that one file, auto-merges it and tags the merge commit with an annotated tag (the current ones are lightweight, which is why `V0.1.0` could be mis-cased and any of them could be moved). Guards: a `release` concurrency group; refuse to move an existing tag; a schema or verb-set change forced to `minor` or higher by a gate on `git diff schemas/`.

**2. Pin-bump job on Napoleon (M).** On a new core tag, generate `job/J<n>` with a brief the hook can enforce: bump the gitlink and `[core] version` in one commit, delete game verbs that now collide with core verbs (`CORE_VERBS` diff), update the adapter (C2), add the `stb_image_write` pin, raise the `proxy` CI timeout, run `gates`, `gen_tables --check` and `build.sh all`. Never `meta/` (P3). When the core diff touches `proxy/` or `harness/` (every bump from 0.9.0 does), the row is `needs_pc` and stops at "ready for acceptance"; a bump that touches neither can auto-merge on green CI like a brief. A 2-second `-fsyntax-only` compile of each consumer's `adapter.cpp` against a candidate tag, run by the core's CI before tagging, would have caught C2 before any job started.

**3. Agent-merged `plan/` (S, after P2).** Blast radius today is `docs/**` (including `CLAUDE.md` and `REVIEW.md`), every job row and new briefs. Safe once policy reads `[policy] plan` from the base, `plan/` may not touch `CLAUDE.md`, `docs/REVIEW.md` or `core/docs`, and row edits on `plan/` are limited to new `needs_brief` rows plus `title`, `description` and `depends_on` (no `status`), compared row by row as `brief/` already is. Then `plan/` merges itself on green CI like `brief/` (D33). `meta/` keeps waiting for you. The same rule covers core `plan/` PRs that only touch `docs/BACKLOG.md`.

**4. Brief open questions with defaults (S-M).** Most of the D38, D39 and D47 batch answers were "as recommended". Give each question `recommended:` and `default after: <date>`; `jobs check` lists the due ones and a `plan/` agent applies them as a dated D line naming each; questions tagged `taste`, `risk` or `legal` never default and go to a "waiting on Liam" lane on the status page.

**5. The 20-pass acceptance run unattended (M, PC).** A scheduled PC task that runs `acceptance.py run` for any branch whose rule 79 fails, under these guards: owner equals the session id (H2); refuse while you are active (`GetLastInputInfo` idle time or a `<state>\liam_present` file); refuse when the running watcher differs from HEAD (H10); unique run ids (H5); flake classification so one B60 relaunch does not cost 2.7 hours (H4); commit ledger and evidence with the trailer. Pair it with the watcher self-updating from a kit when the version differs.

**6. Main health (S).** `ci notify` on `main` opens or updates one issue for a red required job; the next push to `main` reruns a set whose last `main` run failed; `jobs next` prints a red `main` before anything else. This closes P1 and is the cheapest item here.

**7. Smaller chores.** An atomic job claim (`git push origin origin/main:refs/heads/job/<id>` as the first step of `jobs next`); the autopilot deferring a review while the branch's CI is red or running, and serialising `needs_pc` rows; `git worktree prune` in the autopilot tick plus a `wsc setup` warning; a `later` row kind with trigger paths (R4); `gen_tables.py --exe` on a staged exe copy so a new engine site is checked in the cloud (C7); a cloud job that symbolises minidumps against the build's map file; a `Usage:` line filled from `usage_reader` (R3); mid-job budget lifts as a row field; a hook allowance for deleting `scratch/*` branches; the recurring one-off permissions (moving `vdisplay_restore.json`, settings edits) turned into guarded verbs.

**What stays with you.** Art and design looks (D35, D43, board locks), release values and budgets (R2), scope adds under D14, the own-code licence and the unofficial-mod statement, `releases.json` when publishing, GitHub repository settings, WER and admin-rights changes on the PC, anything needing your saves or your play. The status page should show these as one lane so they do not arrive as chat interruptions.
