Of the three moonshots, the external battle AI is the one the project is already closest to enabling and the one with the clearest evidence-based path, so it should be filed first: the engine's own order chain (Selection → move/formation constructor → queue push) and the UNIT/entity layout are located and anchor-checked at every start, the harness already loads a battle in ~4 s on a hot PC, pauses it, runs it at up to **4.0x** and warm-resets it in **27-33 s**, and the prior art says a scripted hierarchical AI beats a shipped planner at hobby scale while reinforcement learning does not become credible until one instance runs at **≥20x and ≥2,000 episodes a day**. The recommended sequence is gym substrate on J28, then a parametrised utility/influence-map AI playing the player's side against the vanilla AI, then evolutionary tuning, and behaviour cloning plus RL only after three measurements pass their gates (speed-up beyond the 4x cap via a clock hook, episodes per day, replay determinism). The lighting/post-plus-volumetric-smoke feature has a precise hook (the six-draw composite in pass 6), an fx-source route the fixed-sky dev pack has already proven, and published costs that fit **2.5-4.5 ms added GPU time at 4K on an RTX 4090**, but it reverses an explicit PLAN section 2 exclusion and starts from a capture gap (no firing battle has ever been captured, so the smoke draw count under fire is unmeasured). Ray-traced shadows and AO are blocked before they start: stock DXVK never enables the Vulkan RT extensions, and NVIDIA's 32-bit Windows ICD does not expose them at all (two independent reports, 2019 and 2026-10-29); a ten-minute `SysWOW64\vulkaninfo` probe on Liam's 4090 settles it, and the expected negative leaves only the out-of-process 64-bit bridge PLAN section 2 already excludes, so the verdict is defer. The Empire smoke backport is undetermined rather than hard: the shader diff is modest (`particle.fx` 76 lines, the volumetric fragment 456) but Napoleon's 94 effect definitions were never diffed file by file against Empire's 74. The final section gives, for each feature, a verdict, a dated decision line in the repo's form, job rows in build order with kill criteria, and the changes to existing briefs (J28, J30/B36, J23, J46, the Empire restart list).

## The order path is located but unrun, and the enemy side is uncharted

J9's static pass delivered the whole command chain the UI itself uses: a `Selection` constructor at 0x68f580 (a 0x44-byte object), `AddUnit` at 0x6a0480 (which refuses a unit whose state byte `[UNIT+0xaa0]` is 0 or 2), the move/face command constructor at 0x599760 taking `(Selection*, loc[5]*, int16 angle, float width, bool run, bool queue)`, the queue push at 0x58dc00 onto `[[[0x14a418c]+0xf8]+0x28048]`, a formation constructor and push pair, and the command destructor, plus a pre-check on `[battle+0x281e4]` that can drop an order (repo: `harness/runs/20261101_j9pc/j28_candidates.md` section 2). Nine of these are registered as verify-only `engine_sites` rows with anchor bytes and passed the start-up check "45 sites: 45 ok, 0 bad" on the J9 acceptance run (repo: `registries/engine_sites.jsonl`; `jobs/J9/review.md`). The unit side is equally concrete: the active entity is `E = [UNIT+0xadc + 4*[UNIT+0xae8]]`, live position floats sit at `[E+0x6dc..0x6e4]`, facing is an int16 at `[E+0x64c]` (65536 = 360°), men alive at `[UNIT+0x204]`, the army at `[UNIT+0x1ec]` with its unit array at `[army+0xf4]`, and the entity's queued-order count at `[E+0x460]` (repo: `j28_candidates.md` 1b). Nothing in this chain has been called live: J28 ("Battle unit control route", `queued`, Opus, depends on J4, J9, J44) is the job that turns it into an `order` verb with readback thresholds of 1.0 m / 1.0° / 0.5 m, one command per unit, calls on the Lua pump thread, and a ~350-call budget whose kill criteria include a pushed command that moves nothing after three attempts (repo: `registries/jobs/J28.json`; `jobs/J28/brief.md`).

What is **not** located matters for any AI that wants to be Napoleonic rather than geometric. Formation front centre and width are "probably UNIT+0x310 and UNIT+0x324" by structural inference only; ranks have no anchor; morale, fatigue, ammunition and the run flag have no UNIT offsets in any repo file (repo: `j28_candidates.md` "Not found / open"). The exe does carry the battle-script getters `is_routing` and `ammo_left` as Lunar-table entries, and the morale and fatigue state name strings (`morale_broken ... morale_wavering`, `fatigue_fresh ... fatigue_exhausted`) each have one code reference (repo: `discovery/napoleon/exe_strings.tsv.gz`), so these are traceable RE items rather than unknowns, and SMACv2's finding that **enemy health was the single most important input feature** across its scenarios says the men-alive field already located carries most of the signal ([SMACv2](https://ar5iv.labs.arxiv.org/html/2212.07489)).

The route J28 takes is the right one and the project should keep its prohibition. The Lua script API is refuted as a route: `empire_battle`, `battle_manager` and the controllers are nil in the pumping battle UI Lua state, and `require "Scripting_Library"` adds only Lua helpers (repo: `registries/engine_facts/napoleon.battle.script_api_reachable.json`, refuted 2026-10-29, run `harness/runs/20261029_j4pc`). Every public precedent that drove Total War units from outside chose the Lua route and paid for it: Attila-AI (2026) attaches a battle script and re-takes control of every AI unit on every pump because "a take is not durable", found that "engine-touching verbs" are conflict-phase only after deployment execution froze its dispatch, and runs everything off a single `register_repeating_timer(..., 100)` because a second timer kills the dispatch ([Attila-AI aai_run5.lua](https://raw.githubusercontent.com/TheoOltean/Attila-AI/main/src/aai_run5.lua)); the Napoleon Script Extender's battle `lua_State` identification is a sentinel heuristic its author calls "still unverified" ([NSE README](https://raw.githubusercontent.com/Nymber/Napoleon-Script-Extender/main/README.md)). J28's direct chain is the BWAPI pattern, an in-process DLL calling the engine's own constructors ([bwapi.github.io](https://bwapi.github.io/)), and it is the only route that is replay- and multiplayer-safe by construction if the lockstep inference below holds.

The uncharted part is the enemy. J28 builds a Selection from explicit UNIT pointers and pushes to the one queue; whether that queue accepts commands for the AI alliance's units, and whether the `[battle+0x281e4]` pre-check or `AddUnit`'s state test refuses them, is recorded nowhere (repo: `repo_evidence` inference from `j28_candidates.md`). The documented script semantics say `take_control()` removes units from AI control and `release_control()` returns them to an AI that "may then behave oddly", with **no documented "disable AI for an alliance" call** anywhere in the Shogun 2-era API ([Total War Wiki Battle Script Documentation](https://wiki.totalwar.com/w/Battle_Script_Documentation.html)). Three mute candidates exist, none measured. The exe's battle-AI tweakers `BATTLE_AI_EXCLUSIVE` (object 0x14a3b28, "AI versus AI (no manual player control)"), `BATTLE_AI_INVERT` (0x14a3640, "Inversely defaults the AI-controlled force to be the 'other' one") and `TEST_AI_BUILD` ("Exclusive AI resetting and seed-changing game (amount of battles suppl...") are byte initialisers the proxy can already flip in DllMain before the CRT runs them (repo: `harness/runs/20261101_j9pc/tweakers.tsv`; `registries/engine_facts/napoleon.tweakers.table.json`). The DenseCow reverse-engineering notes place the alliance AI object at `alliance+0xC`, its update at 0x007B25A0, and show it is called exactly once per 0.1 s battle tick from 0x005832C0 → 0x00583380, so a guarded skip of that call for one alliance would idle the planner and melee manager for that side only ([DenseCow AI_RESEARCH.md](https://raw.githubusercontent.com/DenseCow/Napoleon-Total-War-Rust-Rewrite/main/analysis/ai/AI_RESEARCH.md)). Two caveats on that: DenseCow is one AI-assisted project's Ghidra work with self-tagged confidence, its addresses are static VAs for 1.3.0.0 that must be anchor-checked on Liam's exe, and a detour there is a D2 feature detour on an engine-internal function, which is beyond J28's "engine calls only, no detours" stance and beyond D26's IAT-only rule for dev hooks (repo: `docs/DECISIONS.md` D2, D26; `jobs/J28/brief.md`). The cheapest path, and the one the roadmap below takes, is the one both research notes converge on: **have the external AI play the player's side against the vanilla AI first**, where no mute is needed, and evaluate it as the opponent only once a mute route is measured.

## One instance at 4x yields a few hundred episodes a day; three numbers decide whether RL is viable

The arithmetic that governs the AI feature is environment throughput, and the repo has already measured every term. `RequestSpeed(ffwd)` is the engine's fastest clock at a measured **4.0x** of wall time (pause 0.0, slow 0.42-0.45, play 1.0, fwd 2.0), the battle clock runs only after deployment ends, and a speed or pause check costs about 10 s (repo: `registries/engine_facts/napoleon.battle.speed_route.json`, verified 2026-10-30, run 20261030_j43pc; `jobs/J43/report.md`). A custom land battle loads in **3.9 s** on a hot PC or **26.4 s** from process start with the intro skipped, settle takes ~2.7 s, and a warm reset back into a deployed battle takes **27.1-33.4 s** with +1.5 MB of address space per cycle (repo: `napoleon.battle.custom_land_load.json`; `napoleon.ctl.settle_signal.json`; `napoleon.reset.battle_warm.json`, verified 2026-10-29, run 20261029_j3pc2). There is no frame-step, no render-off mode and no mid-battle save/restore; every watcher launch is headless on the Virtual Display Driver but still renders; and the single `game.lock` plus D11 mean one environment instance per PC (repo: `harness/README.md`; `docs/DECISIONS.md` D11). From those numbers a 12-minute battle at 4x is ~3 min plus ~30 s of reset, so one instance yields on the order of **150-400 short episodes a day** and roughly 10^4-10^5 macro-decisions a day; the RL note gives 150-350 in its takeaway and ~400 in its inference, and both are upper bounds that assume no crashes and battles that actually end.

That is one to two orders of magnitude short of the cheapest published RL results in this regime. SMAC trains QMIX/MAPPO to near-perfect win rates on 3- to 27-unit maps in **10M environment steps, about 18 hours per run on one GTX 1080 Ti** ([SMAC paper](https://arxiv.org/pdf/1902.04043v2)); Gym-μRTS reached a state-of-the-art agent in ~60 hours on one GPU but needed 300M steps across 24 parallel environments ([Gym-μRTS](https://arxiv.org/pdf/2105.13807)); TStarBot1's macro-action PPO needed ~3,500M frames (~7M games) on 3,840 CPUs to reach 75% against the cheating level-10 SC2 AI ([TStarBots](https://arxiv.org/pdf/1809.07193v3)). The flagship systems are not the comparison: AlphaStar's 3,072 TPU v3 cores plus 50,400 CPU cores for 44 days and OpenAI Five's 770 PFlops/s-days were driven by full-game economy, 10^26 actions and league training, all of which a 20-unit line battle lacks ([TStarBot-X](https://arxiv.org/pdf/2011.13729); [OpenAI Five](https://arxiv.org/pdf/1912.06680)). The persistent cost that does not collapse is **steps per second of one accelerated instance**, which is why TStarBot1 still needed thousands of CPUs; an RTX 4090 is far more than enough for a policy the size of Nexto's 444K parameters ([habr](https://habr.com/en/articles/773454)).

The three measurements that decide RL viability, and the proposed gates, follow directly. First, **speed-up beyond the 4x cap.** The precedent is Highway Pursuit RL, where hooking `QueryPerformanceFrequency`/`QueryPerformanceCounter` in an injected DLL made each step advance exactly one 60 fps frame "as fast as the machine allows", with semaphores running the main loop once per instruction ([Highway Pursuit RL](https://nilsruet.github.io/projects/highway-pursuit-rl)); PySC2 reports 10x "is not uncommon" with rendering skipped ([PySC2 environment.md](https://github.imc.re/hejingpeng/pysc2/blob/master/docs/environment.md)). DenseCow describes the Napoleon battle model as lock-step at 100 ms with "one tick per due scheduler call" at 0x0057DF40 ([DenseCow BATTLE_FIDELITY.md](https://raw.githubusercontent.com/DenseCow/Napoleon-Total-War-Rust-Rewrite/main/analysis/fidelity/BATTLE_FIDELITY.md)), which is the shape of a wall-clock scheduler a timer hook can feed; the timer APIs are kernel32/winmm imports, so this would be an IAT hook of the kind the proxy already installs for user32 and the CRT and would sit inside D26 rather than against it (this is my inference from the two notes; nothing has been tried, and the only verified speed is 4.0x). The gate from the notes: if battle time cannot be decoupled from wall time within one to two jobs, the project proceeds at 4x and RL is deprioritised; **≥20x** is the number at which "hundreds" becomes "thousands" of episodes a day. Second, **episodes per day**, measured end to end with the watcher's crash and hang accounting; the gate is **≥2,000 a day**. Third, **determinism.** The campaign start is not image-deterministic and a custom battle picked its sky per launch until a dev pack pinned one sky per (season, weather, time of day, climate), which is what made the 20-pass shot runs repeatable (repo: `napoleon.campaign.determinism.json`; `napoleon.battle.fixed_sky.json`). On the simulation side the Warscape-internals note argues lockstep from a fixed 0.1 s tick, per-tick "replay/sync logs" at 0x005EDCB0, the battle AI's LCG (`x = x × 0x343FD + 0x269EC3`) and CA's own "desync" vocabulary, and calls it "well-supported inference, not a CA statement" ([DenseCow AI_RESEARCH.md](https://raw.githubusercontent.com/DenseCow/Napoleon-Total-War-Rust-Rewrite/main/analysis/ai/AI_RESEARCH.md); [PC Gamer on the Shogun 2 desync patch](https://pcgamer.com/total-war-shogun-2-patch-tackles-multiplayer-desync-bugs-improves-lighting)); the RL note warns of the SoulsGym outcome, where "results cannot be reproduced by setting RNG seeds, because the games are nondeterministic" ([SoulsGym](https://pypi.org/project/soulsgym)). The two notes do not disagree so much as flag the same unknown from opposite sides: it must be measured by replaying one order stream twice on a fixed preset and hashing the per-unit state vector every N ticks. The gate is determinism good enough that **50-episode evaluation batteries are stable**; if exact replay cannot be reached, evaluate over 50-100 episodes per cell as the competitions do (AIIDE ran 100 games per bot pairing: [AIIDE 2019](https://www.cs.mun.ca/~dchurchill/starcraftaicomp/2019/AIIDE2019_StarcraftAICompetition)).

Two engine facts shape the gym loop whatever the gates say. Armies in a custom battle come from the remembered `.sp_default` preferences, and a fixed 20-versus-20 army needs the army-setup route J46 (`land_40`) owns (repo: `napoleon.custom_battle.armies.json`; `registries/jobs/J46.json`); SMACv2's result that "an open-loop policy conditioned only on the timestep can achieve non-trivial win rates" on fixed scenarios means J46's preset must also be able to randomise army lists and deployment zones, or any learned policy will memorise a timing script ([SMACv2](https://ar5iv.labs.arxiv.org/html/2212.07489)). And any observation chunk that runs in the battle UI Lua must avoid `string.find` (one call stalls the battle pump about a second later; the repo tests already refuse it), with engine bindings reading arguments top-down so extra arguments shift values (repo: `napoleon.lua.string_find_stalls_pump.json`; `napoleon.lua.arg_stream.json`). Battle-end and outcome signals are available without new RE: `BattleUI.PostBattleInfo`, `ExitBattle`, `IsConflict`, `UnitListForBattleIds` and `CombatRatioDetails` all exist as probe-safe getters in the battle state (repo: `discovery/napoleon/lua_cfuncs.json`; `discovery/napoleon/probe_safe.json`).

## A scripted hierarchical AI beats vanilla without learning; RL is a conditional fourth stage

The strongest result in the prior art is that rules beat learning at every budget a solo developer can reach, and that the shipped Total War AI already has the right shape, so the gains come from evaluation and persistence rather than paradigm. At AIIDE 2019 the Brood War winners were rules-based cores with narrow learning, Locutus at **90.24%** and PurpleWave at 88.89%, whose author says "most of what it does is rules-based" ([AIIDE 2019](https://www.cs.mun.ca/~dchurchill/starcraftaicomp/2019/AIIDE2019_StarcraftAICompetition)); TStarBot2, a hand-written two-tier macro/micro bot, beat the cheating level-10 SC2 AI **90%** of the time against the RL TStarBot1's 81% ([TStarBots](https://arxiv.org/pdf/1809.07193v3)); scripted agents won the first five microRTS competitions, and rules-based agents won Halite, Kore and Lux Season 2 ([microRTS 2023 winner paper](https://www.arxiv.org/pdf/2402.08112)). When learning did win, it stood on a scripted teacher: RAI-BC, behaviour-cloned from scripted bots alone, won 71%, and PPO fine-tuning lifted it to 88% in ~49 GPU-days, while from-scratch RL cost ~70 GPU-days and still suffered inference timeouts in the live competition ([same](https://www.arxiv.org/pdf/2402.08112)). Lux is the cleanest warning about reward: a three-phase dense-to-sparse curriculum reached >90% against the Kaggle winner while sparse win/loss alone gave ~0% ([Chen et al.](https://arxiv.org/pdf/2301.01609v2.pdf)).

Creative Assembly's own architecture is the three-layer hierarchy the surveys describe, strategy at a ~3-minute horizon, tactics at ~30 s, reactive control at ~1 s, with only the lowest layer sending commands ([Ontañón et al. survey](https://www.cs.mun.ca/~dchurchill/publications/pdf/starcraft_survey.pdf)). For Warhammer CA described a Grand Tactical Analyser setting stance, objectives assigned to detachments, modular tactics that pass units between each other, a Reserve that reinforces faltering tactics, and influence maps scoring "attack focus" points ([Game Developer, War Hammer part 5](https://www.gamedeveloper.com/design/war-hammer-the-ai-of-total-war-part-5-)); Bannerlord's formation AI "uses the same interface and commands as the player: our combat AI doesn't cheat!" ([Bannerlord dev blog](https://www.gamebanshee.com/k4h4h)); Ultimate General runs a no-bonus GOAP with reserves, high ground for artillery and nine commander personalities ([Ultimate General AI](https://www.ultimategeneral.com/blog/game-features-ai)). CA itself has moved the engagement evaluator to a learned model: Kwan and Cakmak's AIIDE 2025 paper predicts 1v1 unit combat outcomes "as an alternative to a heuristic, rules-based approach" for the auto-resolver and for "informing battle AI decisions about whether units should engage or retreat" ([Kwan & Cakmak, AIIDE 2025](https://ojs.aaai.org/index.php/AIIDE/article/view/36830)).

The DenseCow reverse engineering explains why fifteen years of data mods changed the feel but not the behaviour of Napoleon's AI, and therefore why an external AI is the only route to "better than vanilla". There is **no battle-AI DB table in Napoleon**; the plan vote runs every 10 updates with twelve counters and plans that "never win" because their inputs are constant, the attacker "always attacks", and the tactic auction scores are literals: ATTACK_BATTLEGROUP 1, LIMBERED_ARTILLERY 164 whenever a free gun exists, STOP_AND_SHOOT 164 at CONTACT, OUTFLANK `100 + seed % 65`, DOUBLE_ENVELOPMENT `80 + seed % 65`, with STOP_AND_SHOOT's efficiency window of 200 ticks and 0.01 kills per unit per tick before it creeps forward ([DenseCow AI_RESEARCH.md](https://raw.githubusercontent.com/DenseCow/Napoleon-Total-War-Rust-Rewrite/main/analysis/ai/AI_RESEARCH.md)). Those constants map onto the reported failures: GameSpot's Prussians who "march up and down the map edge instead of storming" then make "a desperate, careless attack" ([GameSpot review](https://www.gamespot.com/reviews/napoleon-total-war-review/1900-6252611/)), cavalry that "always stops short" ([TWC](https://www.twcenter.net/threads/ai-cavalry-misuse.258221/)), and the "player wins about 90% of the time" even with AI mods that "mostly add buffs or aggression rather than real intelligence" ([Steam NTW thread](https://steamcommunity.com/app/34030/discussions/0/3201493200078605831)). Difficulty is stat bonuses, not behaviour: DenseCow's consumer at 0x006AD6E0 adds +4 attack at level 1 and +8 at level 2 for the AI, reduced by one level per five units the AI outnumbers the enemy ([same](https://raw.githubusercontent.com/DenseCow/Napoleon-Total-War-Rust-Rewrite/main/analysis/ai/AI_RESEARCH.md)); CA only began difficulty-dependent behaviour with Three Kingdoms ([CA blog](https://www.totalwar.com/?p=13725)). That makes "beats shipped AI" definable by the project's own batteries: the notes propose **≥80% win rate against vanilla Normal at equal stats and ≥60% against Hard with its bonuses, over 50-episode batteries on three or more maps**, which converts to roughly 240 Elo or an 8.3 TrueSkill gap ([OpenAI Five](https://arxiv.org/pdf/1912.06680)).

The concrete design the notes converge on is a padded per-unit table (own and enemy, ~12 floats each: ground-plane x/z, bearing sin/cos, men-alive fraction, type one-hot, is_moving, has_order, and routing/fatigue once getters exist) rather than pixels, as SMAC and TotalBotWar do ([SMAC](https://arxiv.org/pdf/1902.04043v2); [TotalBotWar](https://www.arxiv.org/pdf/2009.08696)); macro-orders per unit or group every ~5 s of battle time (move-to-line with facing and width from a small set of relative waypoints, face, attack-unit, formation, fire mode, charge, limber), with a 1 s reactive layer in scripted code for square-versus-cavalry and withdraw-when-flanked, which gives 100-200 policy steps per battle and a joint action far smaller than TStarBot1's 165 zone-pair macros; group-level assignment from a tiny script portfolio, which Portfolio Greedy Search showed dominates per-unit action search at 16 or more units ([Churchill & Buro](https://www.cs.mun.ca/~dchurchill/publications/pdf/combat13.pdf)); a shaped reward on casualty differential and routs with a terminal win term scaled SMAC-style to ~20; and a curriculum from one line versus one line through 5v5 to 20v20 with randomised armies, deployments, weather presets and AI difficulty sampled per episode as TStarBot1 did. The RL note's own ranking of risks is worth keeping verbatim in the brief: order-path thread and AI-interference failures (unknown, mitigated by readback and by playing the player's side), non-determinism making evaluation noisy, crash rate at high speed-up (the mss32.dll fast-quit crash is already mitigated by an 8 s settle; the watcher owns relaunch), missing observables, and sieges and naval needing their own action sets and probably their own AIs, which CA itself needed for Fall of the Samurai ([AI of Total War part 3](https://www.gamedeveloper.com/design/revolutionary-warfare-the-ai-of-total-war-part-3-)).

Evolutionary tuning is the middle path that is almost certain to show a gain and that fits the 4x world. García-Sánchez et al. evolved a complete Brood War strategy with a population of 30 over 30 generations, 12 games per individual, in ~120 hours on eight VMs with 10-minute games, and the result beat the base bot 6 of 10 ([García-Sánchez et al.](https://human-competitive.org/sites/default/files/garcia-sanchez-merelo-mora-squillero-tonda-paper.pdf)); Liu et al. encoded micro behaviours in fourteen parameters and out-kited the competition bots ([bearworks](https://bearworks.missouristate.edu/articles-cnas/2797)). At ~400 episodes a day a 16-individual by 15-generation CMA-ES run over 10-50 named parameters is 1,000-2,000 battles, three to five days of unattended watcher time; at 20x it is a day. Behaviour cloning then needs only tens of thousands of (state, order) pairs from the scripted AI's trajectories, with PPO fine-tuning at SMAC-scale GPU cost but environment-bound wall time (weeks at 2,000 episodes a day for ~10^6 decision steps). A second BC source is the vanilla AI itself: the queue push site J9 located is where every AI-issued order passes, so a read hook there logs (state, order) pairs for free, and `BATTLE_AI_LOG_MELEE` already spools the melee manager's decisions to `battle_ai_melee_log.txt` (repo: `tweakers.tsv`). LLM agents have no place in the order loop and every place in authoring it: TextStarCraft II assumed ~1.66 s per call and kept micro rule-based, SwarmBrain managed ~6 inferences a minute and built a reflex state machine because matching the game's tempo "is currently unrealistic", and AVA measured 1.2-4.5 s per VLM step against 8-10 ms for a trained MARL policy ([arXiv 2312.11865](https://arxiv.org/html/2312.11865v1); [arXiv 2401.17749](https://arxiv.org/pdf/2401.17749); [arXiv 2503.05383](https://arxiv.org/pdf/2503.05383)). The Claude Code agents write and tune the scripted layers and the evaluation batteries; they do not play.

## The composite is a six-draw hook, and froxel smoke fits a 4-6 ms budget

J8's captures give the lighting feature an exact insertion point and an exact seed. A land_small frame at 1080p on DXVK runs eight passes: a 2048 R16F + D24X8 shadow map (49 draws), half-size reflection and refraction targets, a **main pass of 454 draws into a 1920x1080 A8R8G8B8 target with a D24S8 depth-stencil** (vegetation 342, grid 69, unit 12, imposter 9, particle 4, sun 1), a 19-draw `sprite.fx` pass of unit banners labelled "Drawing sneaky sprites", a **six-draw composite to the backbuffer** reading the main target at s0 (one `hdr_to_screen.fx t0_sm3` draw with a `colour_matrix` and `g_brightness` 1.2, five `lenseflare.fx` draws), and a 65-draw UI pass; there is no HDR chain, no SSAO, no depth of field, no depth prepass and no MSAA (repo: `discovery/napoleon/frame_anatomy.md`; `harness/runs/20261101_j8pc/captures/r1_land_small.json`; facts `napoleon.render.pass_order`, `napoleon.render.targets_backbuffer`, verified 2026-11-01, run 20261101_j8pc). Pass 6 begins with `SetRenderTarget(0, backbuffer)` after the sprite pass, and the capture hooks already see `SetRenderTarget`, `SetTexture`, the draws and the `hdr_to_screen` shader hash, so a detour can substitute its own tonemap and post chain at that draw. The depth is the catch: the main-pass depth is a D24S8 **surface**, not a texture, so a post pass that needs depth must either force the engine's own `ENABLE_DEPTH`/`DEPTH_BUFFER_FORMAT_INTZ` macros, which exist in the shipped macro set, or substitute an INTZ texture at creation (repo: `r1_land_small.json` surfaces; `napoleon.shaders.macros.json`). That substitution is exactly what ReShade does on D3D9, replacing the auto depth-stencil at `CreateDepthStencilSurface` with an INTZ texture and refusing multisampled depth ([reshade d3d9_device.cpp](https://raw.githubusercontent.com/crosire/reshade/main/source/d3d9/d3d9_device.cpp)), and DXVK maps INTZ to `VK_FORMAT_D24_UNORM_S8_UINT` with a depth|stencil aspect, binds a sampled depth target read-only when Z-write is off, and falls back to `VK_IMAGE_LAYOUT_ATTACHMENT_FEEDBACK_LOOP_OPTIMAL_EXT` otherwise ([dxvk d3d9_format.cpp](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/d3d9/d3d9_format.cpp); [dxvk d3d9_device.cpp](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/d3d9/d3d9_device.cpp)). RESZ is AMD-only in DXVK and dxvk-nvapi does not forward `NvAPI_D3D9_*`, so neither of TESReloaded's depth-copy paths applies; INTZ sampling with Z-write off is the route ([jp7677/dxvk-nvapi](https://github.com/jp7677/dxvk-nvapi)).

The fx-source route makes Napoleon strictly easier than ENB's or TESReloaded's targets. Napoleon compiles its shipped fx sources at runtime through `d3dx9_40`, and compiling them with the same DLL reproduces the runtime shaders byte for byte (repo: `napoleon.shaders.runtime_compile`); the fixed-sky pack already proves that a type-4 dev pack served through `dev.file_rules` overrides shipped files with "zero bytes written into data\" (repo: `napoleon.battle.fixed_sky.json`; `jobs/J44/report.md`). So adding a `COLOR1`/`COLOR2` G-buffer output (view-space normal, material id) to each opaque technique is a finite source edit, not a bytecode patch, which is what TESReloaded does by replacing Gamebryo's named shaders with recompiled HLSL ([TESReloaded ShaderManager.cpp](https://raw.githubusercontent.com/mcstfuerson/TES-Reloaded/master/TESReloaded/Core/ShaderManager.cpp)) and what Skyrim Community Shaders does at D3D11 scale ([Community Shaders 1.0](https://www.nexusmods.com/skyrimspecialedition/articles/9415)). Here the notes diverge in mechanism and the repo settles it: the lighting note assumes a `D3DXCreateEffectFromFile` hook injecting `pDefines` and an `ID3DXInclude`, and the RT note asserts "the project already rewrites shader bytecode", but the repo shows only `GetFunction` reads of bytecode in the capture and the dev-pack route as the proven override; the dev pack is the mechanism to brief. The D3D9 MRT rules that bind are that alpha test compares `oC0` only (so alpha-tested foliage keeps working if `oC0` keeps the alpha), fog is defined only for RT0, blend state is shared across targets (so blended water and decals need `COLORWRITEENABLE1..3 = 0`), and "No antialiasing is supported" ([Microsoft Learn MRT](https://learn.microsoft.com/en-us/windows/win32/direct3d9/multiple-render-targets)); DXVK advertises the independent-bit-depth and write-mask caps and 32768 ps_3_0 instruction slots, so the real ps_3_0 ceilings are 10 `v#` interpolators and 224 float constants ([dxvk d3d9_adapter.cpp](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/d3d9/d3d9_adapter.cpp); [Microsoft Learn ps_3_0 registers](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx9-graphics-reference-asm-ps-registers-ps-3-0)). Alpha-to-coverage under DXVK on NVIDIA needs a multisampled target and MRT forbids MSAA, so the G-buffer pass must use alpha test, never ATOC ([dxvk d3d9_device.cpp](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/d3d9/d3d9_device.cpp)).

Volumetric smoke seeded from the engine's own sprites follows the Frostbite and Call of Duty pattern rather than replacing sprites with ray-marched volumes. Hillaire's froxel system voxelises particles into an extinction volume, lights the froxels from the cascaded shadow map, integrates front to back and applies per pixel, with Halton jitter and a 5%-current-frame reprojection; on a PS4 at 900p and 64 slices it cost **2.95 ms at 8x8-pixel tiles or 0.83 ms at 16x16**, and voxelising 1,000 particles cost 0.03-0.25 ms ([Hillaire, Frostbite SIGGRAPH 2015](https://www.slideshare.net/DICEStudio/physically-based-and-unified-volumetric-rendering-in-frostbite)); Wronski's Assassin's Creed 4 fog cost 1.1 ms on Xbox One at 160x90x64 ([Wronski AC4 GDC slides](https://bartwronski.com/wp-content/uploads/2014/03/ac4_gdc.pdf)); Infinite Warfare's rule is that "volumetrics provide low-frequency fog, while lit particles provide high-frequency detail", with the passes bandwidth-bound and temporal reprojection doubling bandwidth ([Activision COD:IW 2017](https://www.activision.com/cdn/research/2017_DD_Rendering_of_COD_IW.pdf)); Unreal's fog is ~3 ms on a GTX 970 at Epic and warns of "lighting trails from fast-changing lights, such as flashlights and muzzle flashes" ([UE docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-fog-in-unreal-engine)), which is a direct warning for musket volleys. What the proxy sees per `particle.fx` draw today is the camera-aligned axes, wind vector, gravity, time, `g_tpage_info` and the stream handles, not buffer contents; reading sprite positions means a `Lock`/`Unlock` hook that does not exist yet, and the committed summaries have no `DECL`/stride for the particle draws (the raw `frame.txt` files sit uncommitted in `_scratch`) (repo: `discovery/napoleon/shader_catalog.json`; `core/proxy/src/capture.cpp`; `jobs/J8/report.md`). Two shipped facts suggest probing before building: Napoleon ships an 856-line `particle_volumetric.fx_fragment` (changed by 456 lines from Empire), a `volumefog.fx`, an `ENABLE_OFFSCREEN_PARTICLES` macro and a `gfx_volumetric_effect` preference string with "volumetric fog on sea battle" (repo: `discovery/diff/shaders.json`; `exe_strings.tsv.gz`), none of which appear in any capture because the prefs had them off; whether the engine's own volumetric path can simply be switched on is an unmeasured question that could shortcut the first milestone.

The cost model says the budget is realistic if multi-bounce GI stays out. XeGTAO High costs ~1.4 ms at 2160p on an RTX 3070 (20.3 TFLOPS) and the 4090 has 82.6 TFLOPS and roughly twice the bandwidth, so a GTAO-class pass lands around 0.5-0.8 ms at 4K ([GameTechDev/XeGTAO](https://github.com/GameTechDev/XeGTAO); [Wikipedia RTX 40 series](https://en.wikipedia.org/wiki/GeForce_RTX_40_series)); the lighting note's sketch is G-buffer writes 0.2-0.4 ms, AO 0.5-0.8, froxel smoke 0.8-1.5 at 16x16 tiles (1.5-2.5 at 8x8), re-lit soft sprites 0.3-0.6, HDR composite and tonemap 0.3-0.5, TAA 0.3-0.6, for **~2.5-4.5 ms added** on a base frame that itself grows from the measured ~2 ms p50 at 1080p (repo: `harness/acceptance/baseline.json`) to a probable 3-5 ms at 4K; every 4090 number is extrapolated from 3070, PS4 and GTX 970 figures because no source measured a 4090. The biggest cost risk is specific to D3D9: Frostbite and COD run their volumetrics in compute, and SM3 pixel shaders have no shared memory or UAVs, so expect 1.5-3x the compute-equivalent cost, or take the escape hatch that stock DXVK does allow, `ID3D9VkInteropDevice` for a Vulkan compute pass in the same process, which needs no RT extensions and only manual synchronisation ([dxvk d3d9_interfaces.h](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/d3d9/d3d9_interfaces.h)). TAA ghosting on moving units is the other known qualitative failure: camera-only reprojection is right for terrain and trees, wrong for cavalry and smoke, and per-object motion needs a `prevWorldViewProj` constant and velocity output in the same fx edit, with RTX Remix's option list as the catalogue of hard cases (skinned and instanced soldiers, unreliable world matrices) ([Karis TAA](https://de45xmedrsdbp.cloudfront.net/Resources/files/TemporalAA_small-59732822.pdf); [dxvk-remix RtxOptions.md](https://github.com/NVIDIAGameWorks/dxvk-remix/blob/main/RtxOptions.md)). Plumbing-wise the proxy is ready but unfinished: it hooks vtable slots in place with no device wrapper, `hk_Present` already runs proxy code on the render thread with the device pointer, 36 more slots are armed behind `dev.capture`, and `backend.cpp` carries the note "No D3D hook is installed here yet; when a feature adds one it must ask Rt().plan.d3dHooks" (repo: `core/proxy/src/dev.cpp`; `core/proxy/src/backend.cpp`). Three repo constraints apply to every pass: doubles behave as 24-bit floats on the engine thread after device creation (repo: `napoleon.proxy.fpu_precision`), the system d3d9 backend currently presents without reaching the hook at all so a composite pass is untestable there until J61 (repo: `napoleon.render.system_backend.json`), and there is no GPU-time-per-pass instrument, only frame time, which core backlog B34 (state-block hooks) and J23 would have to supply before any budget gate can be enforced (repo: `warscape-core/docs/BACKLOG.md` B34; `registries/jobs/J23.json`).

### The Empire smoke backport is undetermined, not hard

Both games use the same HLSL effect layout and the same PFH0 pack format, Napoleon ships 136 fx sources against Empire's 141 with 71 identical and 61 changed, and the smoke-relevant files differ modestly: `particle.fx` changed by 76 lines with no techniques added or removed, `particle_volumetric.fx_fragment` by 456, `particle_distortion.fx` and `volumefog.fx` by one line each, while `particle2.fx`, `explosion_particle.fx`, `sea_particles.fx` and `weather.fx` are identical and `ribbon.fx` (196 lines) and `lenseflare.fx` are new (repo: `napoleon.diff.shaders.fx.json`, verified 2026-10-29; `discovery/diff/shaders.json`; `discovery/diff/packs.json`). The unknown is the effect data: the diff counted **94 `effects` entries in Napoleon's data.pack against 74 in Empire's main and patch packs** with the verdict "adapter: look it up in the other pack(s)", no per-file diff of names, formats or changed/new status, no `effects/` rows in `registries/assets.jsonl`, and no format note in the diff README (repo: `discovery/diff/packs.json`; `discovery/diff/README.md`). The db side adds `particle_effects` (104 key-only rows), `projectiles_explosions` and `projectile_trails` on Napoleon, whose Empire counterparts were not compared either (repo: `discovery/db/tables.json`). Feasibility therefore turns on one unperformed diff and on whether Empire's exe accepts Napoleon's effect-definition format, which no note records; the cheap first step is a per-file `effects` diff run from the Napoleon repo's existing `discovery/diff` tooling, with `empire-remastered` read as evidence only, which is already the rule for Napoleon work (repo: `CLAUDE.md` D30).

## Ray tracing stops at the 32-bit NVIDIA ICD unless a ten-minute probe says otherwise

DXVK's interop gets a third party most of the way and then stops at exactly the extensions ray tracing needs. `ID3D9VkInteropDevice`, added in DXVK 2.0 (2022-11-10), returns the `VkInstance`/`VkPhysicalDevice`/`VkDevice` and the graphics `VkQueue` with its family index, and its `FlushRenderingCommands` → `LockSubmissionQueue` → `vkQueueSubmit` → `ReleaseSubmissionQueue` protocol lets a proxy submit its own command buffers between any two D3D9 calls, with the warning that "while the submission queue is locked, no D3D9 methods must be called from the locking thread"; `ID3D9VkInteropTexture::GetVulkanImageInfo` exposes the game's render targets as `VkImage` plus layout (queryable on surfaces since 2.4.1), and `CreateImage` (2.5) creates D3D9 textures with extra usage such as `STORAGE_BIT` ([dxvk d3d9_interfaces.h](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/d3d9/d3d9_interfaces.h); [doitsujin/dxvk git history](https://github.com/doitsujin/dxvk/commits/master/src/d3d9/d3d9_interfaces.h)). Nothing exports vertex or index buffers as `VkBuffer` (the full header history contains no buffer, semaphore or fence interface), so geometry would be shadow-copied from `Lock`/`Unlock` the way dxvk-remix's `processVertices` does ([dxvk-remix d3d9_rtx.cpp](https://raw.githubusercontent.com/NVIDIAGameWorks/dxvk-remix/main/src/d3d9/d3d9_rtx.cpp)). The hard stop inside DXVK is extension enabling: `DxvkAdapter::createDevice()` takes extra device extensions only from registered providers, which are the OpenVR and OpenXR Wine/Proton hooks, and the provider path adds extension names but not the `VkPhysicalDeviceRayQueryFeaturesKHR` feature structs, so **stock DXVK's `VkDevice` is created without `VK_KHR_ray_query` or `VK_KHR_acceleration_structure`** ([dxvk dxvk_adapter.cpp](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/dxvk/dxvk_adapter.cpp); [dxvk_instance.cpp](https://raw.githubusercontent.com/doitsujin/dxvk/master/src/dxvk/dxvk_instance.cpp)). A patched DXVK adding a config option mirroring `enableNvCudaInterop` is about 50 lines, but it reverses the proxy's own pin, "Stock DXVK, latest stable release when pinned ... Never a fork (proxy job decision)", on 3.1.1 with its sha-pinned tarball (repo: `core/proxy/tools/fetch_dxvk.py`). Nothing in `core/proxy/src/` touches any interop interface or Vulkan symbol today (repo: `repo_evidence` grep of `core/proxy/src/`).

The blocker that precedes even that is the driver. The most specific datapoint is from **2026-10-29**: on an RTX 4080 SUPER with NVIDIA driver 621.01, `vulkaninfo` from System32 (64-bit) lists `VK_KHR_ray_query` and `VK_KHR_acceleration_structure` while the SysWOW64 (32-bit) run lists neither, which is why the 32-bit Vulkan renderer ao-vk reports "no ray tracing extensions" on Windows ([wannabuh/ao-vk issue #22](https://github.com/wannabuh/ao-vk/issues/22)). A 2019 report on driver 430.86 found `VK_NV_ray_tracing` missing in a 32-bit build of NVIDIA's own tutorial while the 64-bit build worked, with no NVIDIA answer ([NVIDIA Developer Forums thread 76896](https://forums.developer.nvidia.com/t/cant-find-the-vk-nv-ray-tracing-on-32bits-application-works-on-64bits-driver-430-86/76896)). NVIDIA's own Remix documentation states that "Remix itself is a 64-bit program (which is a requirement for using Vulkan ray-tracing)", which is why the entire Remix bridge, a 32-to-64-bit marshalling layer for every D3D9 call, exists ([dxvk-remix RemixRuntimeBinaries.md](https://raw.githubusercontent.com/NVIDIAGameWorks/dxvk-remix/main/documentation/RemixRuntimeBinaries.md)); its build system refuses x86 outright. The same 32-bit DLL does get the extensions under Wine, where WoW64 thunks reach the 64-bit Linux driver and ao-vk's ray-query probe passed on an RTX 4070 Ti ([ao-vk docs/rt-plan.md](https://github.com/wannabuh/ao-vk/blob/main/docs/rt-plan.md)), so the limitation is NVIDIA's Windows 32-bit ICD, not Vulkan or the hardware. No NVIDIA primary statement exists; the evidence is two user reports six years apart plus NVIDIA's design choice, and the RT note flags it as such. **The first ten-minute test** is therefore not a build: run `C:\Windows\SysWOW64\vulkaninfo.exe` (or a ten-line 32-bit probe calling `vkEnumerateDeviceExtensionProperties`) on Liam's 4090 with the current driver and look for `VK_KHR_ray_query`, `VK_KHR_acceleration_structure` and `VK_KHR_deferred_host_operations`; compare with the System32 run; file the result as an `engine_facts` row with the driver version. If the extensions are absent, as expected, in-process RT inside Napoleon.exe is dead on Windows regardless of DXVK patches, and the only architecture left is a 64-bit helper process owning the RT device, fed geometry and camera over shared memory and returning a shadow/AO mask as a shared `VkImage` imported through DXVK's external-memory path, which the RT note sizes as "a multi-week job before the first ray" and which is, in substance, the "64-bit bridge" PLAN section 2 excludes (repo: `docs/plans/PLAN.md` section 2). RTX Remix itself is not an alternative: NVIDIA's compatibility page (updated 2026-10-30) says "DirectX 9.0c games are usually mostly shader-based and probably won't work", its vertex capture needs the game to also set fixed-function `D3DTS_*` matrices, and its skinning path returns immediately for any programmable vertex shader, so Napoleon's shader-skinned soldiers are outside it ([NVIDIA RTX Remix compatibility](https://docs.omniverse.nvidia.com/kit/docs/rtx_remix/latest/docs/introduction/intro-compatibility.html); [dxvk-remix d3d9_rtx.cpp](https://raw.githubusercontent.com/NVIDIAGameWorks/dxvk-remix/main/src/d3d9/d3d9_rtx.cpp)).

If the probe unexpectedly passes, the costs are the next gate and they are dominated by soldiers, not pixels. NVIDIA's guidance is ~100 M primitives/s for full builds and ~1 G/s for refits with acceleration-structure work kept at or under 2 ms a frame ([NVIDIA RTX Best Practices 2019](https://developer.nvidia.com/blog/rtx-best-practices/)); Metro Exodus held BLAS+TLAS to ~0.5 ms on an RTX 2080 by refitting only 16 priority instances plus 4 random ones per frame and culling 100k candidates to under 5k ([4A Games GTC 2019](https://developer.download.nvidia.com/video/gputechconf/gtc/2019/presentation/s9985-exploring-ray-traced-future-in-metro-exodus.pdf)). Two thousand skinned soldiers at ~4k triangles is ~8 M triangles, roughly 8 ms of refit at Turing rates and still several milliseconds on a 4090, so per-soldier refit every frame is out; the workable designs are a shared BLAS per (unit mesh, animation clip, pose bucket) instanced across soldiers in that pose, which requires understanding how the engine's bone palettes map to clips (an unresearched gap), or keeping soldiers in the shadow map as casters while rays handle terrain, buildings and trees, which is precisely ao-vk's shipped split: rays for static opaque and cut-outs, the shadow map for "swaying plants, canopies' leaves and characters' hair", and translucent receivers still reading the map ([ao-vk CHANGELOG](https://github.com/wannabuh/ao-vk/blob/main/CHANGELOG.md)). The RT note's 4K-on-4090 sketch is 1-2 ms for one sun shadow ray with first-hit termination, 1-2 ms for two short AO rays, 0.6-1.5 ms of denoising and 0.5-2 ms of AS maintenance, **4-8 ms in total**, every figure a scaling from 2080 Ti, Titan V and 4070 Ti measurements. Because Napoleon is forward-shaded and samples its shadow map inside the material pixel shaders, the RT visibility mask has to exist before the main pass draws, which means a depth prepass the engine does not run today and an fx edit multiplying the shadow term by a mask lookup; both are the same depth-as-texture and dev-pack-fx work the lighting feature needs, so feature 3 cannot start before feature 2's first two jobs land. Licensing is clear in both directions: DXVK and dxvk-remix are zlib/libpng, so a patched DXVK may be redistributed as `d3d9_dxvk.dll` with the notice and "altered source versions must be plainly marked as such" ([dxvk-remix LICENSE](https://raw.githubusercontent.com/NVIDIAGameWorks/dxvk-remix/main/LICENSE)), and NVIDIA's Remix source files carry MIT headers; NVIDIA's NRD denoiser is **not** open-source-licensed, shipping under the "NVIDIA RTX SDKs LICENSE" with object-code-only redistribution inside an application that has "material additional functionality" and a prohibition on combining with licences requiring source disclosure ([NVIDIA-RTX/NRD LICENSE.txt](https://raw.githubusercontent.com/NVIDIA-RTX/NRD/master/LICENSE.txt)), so a free mod should use an in-house temporal-plus-bilateral or SVGF-family denoiser, which is adequate for a one-channel visibility signal (NRD's own SIGMA shadow denoiser is 0.40 ms at 1440p on a 4080, a useful cost reference even if the code is not used: [NVIDIA-RTX/NRD](https://github.com/NVIDIA-RTX/NRD)). D13's NVIDIA-only scope is consistent with all of this; it is also the reason the 32-bit ICD question is decisive rather than one vendor among several.

## Conclusion

The three moonshots share two substrates, and that is the organising fact for the roadmap. Features 2 and 3 both need depth as a texture, fx-source edits served through the dev pack, a renderer seam (B36) that J30 is about to create, and a GPU-time-per-pass instrument J23 does not yet provide; feature 3 adds a hard external dependency (the 32-bit ICD) that a ten-minute probe either removes or makes permanent, so it is correctly sequenced as a probe now and a feature never, unless the probe surprises. Feature 1 shares nothing with them except the watcher, and its real wall is not GPU or RE but the single game instance at 4x: the engine's constants show the vanilla AI's weaknesses are code paths, not data, which is exactly why an external AI is the only route to "better AI" and why a scripted one can win without learning, while the measured 27-33 s reset and 4.0x cap mean that whether learning ever enters is decided by a clock-hook spike and a determinism measurement, not by ambition.

Two unmeasured engine features could shortcut both tracks and belong at the front of the queue because they are cheap: the `TEST_AI_BUILD` and `BATTLE_AI_EXCLUSIVE` tweakers describe an engine-native "AI resetting and seed-changing" AI-versus-AI batch mode that, if it works, is an episode loop and a self-play substrate for free; and the shipped `particle_volumetric.fx_fragment`, `volumefog.fx` and `gfx_volumetric_effect` preference suggest Napoleon already carries a volumetric path that captures never saw because the prefs had it off. Probing both before writing new systems is the "reuse before you write" rule applied to the engine itself.

### Feature 3: ray-traced shadows and AO through DXVK's Vulkan interop
