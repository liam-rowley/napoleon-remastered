# J80: Pixel gate and tokens: pinned Playwright, wasm hash first, diff threshold, accepted baselines

Phase 5 hardening, from the 2026-11-03 audit (`docs/audits/AUDIT_2026-11-03.md`, findings G10 and G12; "Where each finding went" sends both here). The UI library's pixel gate (J34) is an exact `rgba_sha256` per screen and corner, and four things around it are soft: CI pins Playwright 1.64.1 while `wsc setup` installs it unpinned, so a PC render and a CI render may differ for a reason nobody sees; the recorded `wasm_sha256` is never compared, so a changed viewer build shows up as unexplained pixel changes; one wrong sub-pixel shows as a bare hash mismatch with nothing to look at and no tolerance; and a builder can run `changes.py --accept` on its own work and commit the new baseline. G12 is the token draft: `design/napoleon/tokens.draft.json` (D43) became `uikit/napoleon/tokens.json` by hand with renamed keys, and `test_palette_matches_language` asserts five literals, so it tests the fixture. No game launch, no PC work, nothing under `core/`, `proxy/`, `harness/`, `.claude/`.

Model: Opus (D52: builds run on Opus; the row says opus). Reason: a pixel comparison with a measured tolerance and a policy rule in the hook that judges its own branch. Budget about 70 tool calls; at the cap, stop, commit, report what is left. No subagents.

## What is wrong today (main `3b18a75`, core pinned at v0.10.0; J75 is merged)
1. **Exact hash, no tolerance, nothing to look at.** `uikit/napoleon/gate.py` `render_corners` returns `rgba_sha256` per corner and can write the PNG; `uikit/napoleon/changes.py` `compare` is string equality on those hashes; `tests/test_uikit.py` `test_render_is_deterministic_and_matches_the_baseline` is `assertEqual(res, base)`. The baseline (`uikit/napoleon/baseline.json`) holds only hashes, so there is no reference image to diff against and no way to say "2 pixels moved by 1 level".
2. **`wasm_sha256` is written by `--accept` and never read.** `changes.py` writes it; no code compares it with the `viewer.wasm` just rendered with. A viewer rebuild that changes pixels reads as a UI change.
3. **Playwright is pinned in CI only.** `ci/gates.yml.in` installs `playwright==1.64.1`; `tools/verbs/setup.py` `check_playwright` accepts any version and its fix hint is an unpinned `pip install playwright`; `viewer/pins.json` (the one list of versions the viewer builds from) has no entry. Chromium's revision follows the Playwright version, so the pin is also the browser pin.
4. **A builder can accept its own baseline.** `changes.py --accept` rewrites `baseline.json`; nothing in `tools/jobs_hooks.py` or the core's policy looks at it. After J75 the file is only covered by rule 79's "20 passes" cost for `harness/acceptance/baseline.json`, which is a different file; the UI baseline is not covered at all.
5. **`test_no_lock_file_is_committed_by_this_job`** asserts `uikit/napoleon/LOCK.json` does not exist. It fails the day Liam locks a screen (his file, `{"locked": ["board"]}`, read by `changes.py`), and it is a test of the checkout, not of what a job did.
6. **G12:** `test_palette_matches_language` (`tests/test_uikit.py`, class `Tokens`) compares five colours of `tokens.json` with five literals typed in the test. `design/napoleon/tokens.draft.json` and `uikit/napoleon/tokens.json` share most names but not all (the draft's `line (decorative)` is `line`; `space_dp`, `border_dp` and `icon_dp` became `length` with new names; `on_faction_dark` and `on_faction_light` moved from `color_derived` to `color`; `hover` and `pressed` became computed in `tokens.py`). Nothing checks the copy.

## Decisions already made
1. **One pin, three readers.** `viewer/pins.json` gets `"playwright": {"version": "1.64.1", "why": ...}` (the version CI already uses). `check_playwright` in `tools/verbs/setup.py` reads it, reports the installed version, fails when it differs, and its fix hint is `python3 -m pip install playwright==<pin> && python3 -m playwright install chromium`. `ci/gates.yml.in` keeps a literal (it is rendered text); a test in `tests/test_viewer.py` fails when the literal in `ci/gates.yml.in` differs from the pin. Re-render the workflow with `python3 core/wsc.py ci render`. Bumping the pin is a baseline-affecting change: say so in the pin's `why`.
2. **The wasm hash is compared before any pixel.** `changes.py` hashes the `viewer.wasm` it renders with (it already does for `--accept`) and compares it with `baseline.json` `wasm_sha256` first. A difference is its own finding, printed first and counted in the exit code: `changes: viewer.wasm differs from the baseline's (<short> vs <short>): pixel changes below may come from the viewer build; rebuild and re-accept together`. Pixel rows still print under it, marked `(wasm differs)`. `Render.test_render_is_deterministic_and_matches_the_baseline` does the same comparison before pixels and names the wasm in its failure message. `--accept` writes the wasm hash as now.
3. **A real diff, a threshold, a diff PNG.** The baseline stores one reference PNG per screen and corner (`uikit/napoleon/baseline/<screen>_<corner>.png`, lossless, written by `--accept` from the render's own `R.png_bytes`) next to the hashes in `baseline.json`; the PNGs are committed as binary (`.gitattributes` `-text` for that folder if it is not already covered). Compare in this order: equal `rgba_sha256` = unchanged (the fast path, no PNG read); otherwise decode the reference and the render (stdlib `zlib`, the PNG writer is ours and its format fixed; Pillow only if the stdlib route needs more than about 40 lines) and count pixels whose largest channel difference exceeds `channel_tolerance`; the corner is `within tolerance` when that count is at most `max_changed_pixels` and no pixel exceeds `max_delta`, else `changed`. Dimensions differing is always `changed`. Both numbers and the delta live in `baseline.json` under `tolerance` (so a change to them is a baseline change under Decision 4), with starting values of channel_tolerance 2, max_changed_pixels 0.0002 of the corner's pixels, max_delta 24; **set them from measurement, not from this brief:** render the board 5 times locally if a build exists and in CI, record the observed noise floor (changed pixel counts, max delta) in the report, and set the three values just above it with the reasoning. When it is `changed`, write `<out>/<screen>_<corner>.diff.png` (changed pixels in red over a 30 % dimmed render) and print its path; CI's `viewer` job uploads that folder with the existing `viewer-wasm` artifact (`build/viewer/out/uikit_gate`, `if: always()` upload so a red run keeps its diffs). `within tolerance` is listed by `changes.py` but does not fail; a hash that differs while within tolerance is still reported so drift is visible. `compare` keeps its signature and its tuple rows (the existing `test_compare_and_lock` stays green); the new verdicts come in a new function beside it.
4. **A baseline change must be accepted by someone other than its builder, enforced in the hook.** New rule in `tools/jobs_hooks.py` (a small named function called from `policy_problems`, in the style of J75's): when a branch changes `uikit/napoleon/baseline.json` or any file under `uikit/napoleon/baseline/`, then on a `job/<id>` branch, once `jobs/<id>/report.md` exists at HEAD (the job is handed to review; before that the branch is not yet judged), `jobs/<id>/review.md` must exist at HEAD and contain a line `Baseline accepted: <sha>` where `<sha>` is the git blob sha of `uikit/napoleon/baseline.json` at HEAD (`git rev-parse HEAD:<path>`; the sha changes if the builder edits the baseline after the review, so a stale acceptance fails). The core already refuses a `review.md` written by the session that wrote the report, so the rule does not re-check authorship. A `plan/` or `meta/` branch (Liam's, D50) is exempt; any other kind of branch that changes those files is refused (it has no reviewer). The message starts `ui baseline:` and names the file, the missing or stale line and the sha expected. `changes.py --accept` prints one line after writing: `baseline written; it is not accepted until the reviewer adds "Baseline accepted: <sha>" to jobs/<id>/review.md`, with the sha filled in. `docs/REVIEW.md` gets one sentence beside the rule 79 text (link to the hook).
5. **LOCK.json: the test moves into the hook and the test checks shape.** Delete `test_no_lock_file_is_committed_by_this_job`. Replace with (a) `test_lock_file_if_present_is_valid`: when `uikit/napoleon/LOCK.json` exists it parses, has a `locked` list, and every name is a screen folder under `viewer/napoleon/` with `"library": true` or the board; (b) a hook rule in the same function family: a `job/` branch whose changed set contains `uikit/napoleon/LOCK.json` is refused (`ui lock: LOCK.json is Liam's; a job never writes it`), `plan/` and `meta/` branches are exempt. Test (b) with fixtures; the day Liam commits a lock on a `meta/` branch nothing fails.
6. **G12 through an explicit rename map.** A module-level `DRAFT_MAP` in `tests/test_uikit.py` (or a small helper beside the test, not in `tokens.py`) maps each draft group and name to its `tokens.json` home: `color.*` same name (with `line (decorative)` to `line`), `color_derived.on_faction_dark|light` to `color.*`, `color_derived.hover|pressed` to the computed `derived` rule (compare against `T.derived_colors` within the same ±8 per channel the existing test allows), `space_dp.*`, `border_dp.*` and `icon_dp.*` to `length.*` by name (read both files to build the exact table; the builder lists each rename in the report), `type.*` field by field (`family`, `weight`, `size`, `line`), and the `faction` rules (`default_fill`, `default_on`, `min_on_ratio_all_77`) to their `faction` keys. The new test asserts: every draft entry is mapped or listed in `DRAFT_DROPPED` with a one-line reason; every mapped pair has equal values; every `tokens.json` colour and length is either mapped from the draft or listed in `TOKENS_ADDED` with a reason (a name nobody can trace to the language is a finding); unknown names on either side fail. Replace `test_palette_matches_language`'s five literals by this test (keep its "no spaces in names" assertion). If a value genuinely differs (J34 may have changed one on purpose), do not make the test pass by editing `tokens.json`: list it in `DRAFT_CHANGED` with the reason and the J34 report line that explains it, and put it in the report's open questions for Liam.
7. **No format change to the screens, the library or `tokens.json`.** This job changes how the baseline is judged, not what is rendered. After `--accept` rebuilds the baseline PNGs, the `rgba_sha256` values in `baseline.json` must be **identical** to today's (the render did not change); if any differ, stop (kill criterion).
