## What is wrong today (main 0271d10, core pinned at v0.10.0; J73 is merged, so these are the lines of this tree)
1. **`acc_exempt` (`tools/jobs_hooks.py`) exempts `path.startswith('harness/acceptance/')`**: the ledger, `baseline.json` and `shots/`. Only the ledger must be exempt, because a pass run appends to it. `baseline.json` holds the thresholds and `deterministic`; a branch that edits only it needs zero passes (the audit's example).
2. **`acceptance_problems` counts a line when `result`, `build_id`, `watcher` and `branch` match and `exists(evidence)` is true.** It never reads the evidence file, so 20 copies of one line naming one pass file make a streak of 20. Nothing compares a line with its file (`run`, `pass`, `build_id`, `watcher`, `result` against the file's `build_id`, `watcher`, `passed`, `pass`).
3. **Nothing checks that the ledger diff is append-only.** A branch can rewrite or delete earlier lines (a failed pass turned into a pass, a foreign branch's line relabelled) as long as the last 20 lines look right.
4. **No shas.** `harness/runs/20261103_j24acc3/pass_05.json` holds `build_id`, `watcher`, `kit`, `passed` and the step results, but no shot sha256 and no sha of the kit, DLL or watcher that ran; the ledger line names `watcher` as the hand-kept `$Version` string (H10: a `watcher.ps1` change that keeps `$Version` passes on the old code). The core's `acceptance.py` (`ledger_line`, the pass-file write at the end of `run`) writes none of these at v0.10.0; core W9 (audit train 1, arrives with J78) adds them.

## Decisions already made
1. **Exempt only the ledger.** `acc_exempt` keeps `runs/` folders and READMEs and exempts exactly `harness/acceptance/ledger.jsonl` (`ACC_LEDGER`), by whole-path equality. `baseline.json`, `shots/` and anything else under `harness/acceptance/` become counted paths. A baseline-only change thus needs 20 passes on its final build; J80 adds the stricter content rule on top.
2. **Unique, matching evidence for each counted line.** A line in the streak is counted only when: its `evidence` path was not used by an earlier counted line of the streak; the file parses as JSON; and the file agrees with the line: `build_id` and `watcher` equal, `pass` equal, `passed` true exactly when `result == 'pass'`, `evidence` starts with `run + '/'`, and the step names and ok values agree. The streak's `pass` numbers must also rise by one within one `run` (a pasted line repeats a number). Each failure ends the streak and is named in the rule 79 message, the way `unproved` and `foreign` are today.
3. **Append-only ledger diff.** `collect_acceptance` also reads the ledger at the merge base (`facts['merge_base']`, as `core_pin_diff` does for the pin; fall back to `facts['base']`) into `acc['base_ledger']`. `acceptance_problems` returns a rule 79 error when the base's non-empty lines are not an exact prefix (byte-equal, same order) of the branch's. This runs whenever the ledger text differs from the base's, even when the branch changes no counted path (rewriting the ledger alone is the attack), so it comes before the early `return []` for "nothing to count"; a branch that leaves the ledger alone, or a ledger that is new at the base, costs nothing. A trailing-newline-only difference is not a violation.
4. **Earlier pass files are immutable.** `collect_acceptance` runs `git diff --name-status --no-renames <merge_base> HEAD -- harness/runs`; any `M` or `D` of a `pass_*.json` that exists at the base is a rule 79 error naming the file (adding new ones is the point). `harness/runs/*` stays exempt from counting, so this is its only guard. Core W9 refuses a reused run id at run time; this is the hook-side backstop.
5. **Shas on new lines, switched on by the pinned core, not by a date.** Core W9 will write the shot, kit, DLL and watcher shas into pass files and ledger lines; the field names are the core's to choose, so the hook does not guess them. A helper `acc_sha_fields(root)` loads the pinned core's `core/harness/acceptance.py` source (as `acceptance_active` loads the checker, via `show_first(root, 'HEAD', *ACC_CHECKERS)`) and looks for a module-level tuple `LEDGER_SHA_FIELDS`. If W9 landed under another name, read the core's actual name at the pin, use it and record it in the report. Absent (today, v0.10.0): the sha requirement is off and Decisions 1-4 apply. Present: every counted line must carry each named field as a non-empty hex string, the evidence file must carry the same value, and the shot sha(s) must not repeat across the streak. The field list travels as `acc['sha_fields']` so tests drive it with synthetic tuples and no core. If the name is absent at the pin, put one line in the report for the warscape-core W9 backlog (a note, never a core change).
6. **No format change on this side.** The hook never writes ledger lines or pass files; `core/harness/acceptance.py` stays as pinned.
7. **Messages:** every new error starts `rule 79:` and names the line (`pass N of <run>`), the file and the rule broken, one line per cause.
