Phase 1 hardening, from the 2026-11-03 audit (`docs/audits/AUDIT_2026-11-03.md`: P3, P4, the Python findings on `tools/jobs_hooks.py` and `tests/test_jobs_hooks.py`, and the legacy-set item in "Smaller items"; "Where each finding went" sends all of them here). Today a `meta/` or `brief/` branch, or a pin bump on `meta/`, can move proxy and harness code with zero acceptance passes, and the `proxy` CI input set misses a file the DLL build id hashes. ## What is wrong today (current tree: main 5a76c0d, core pinned at v0.10.0; the audit read 8eec89a with v0.9.0)
1. **Rule 79 runs on `job/` only.** `tools/jobs_hooks.py` `policy_problems` (lines 349-354) returns `[]` unless `facts['kind'] == 'job'`. The core calls the hook for every branch kind (`core/warscape/policy.py` `check`, the hook runs before the `bootstrap` return).
2. **The meta globs are too wide.** `wsc.toml` `[policy] meta` (lines 65-66) lists `core` and `registries/*`. The core matches with `fnmatchcase` (`policy.allowed`, `core/warscape/policy.py:106`), where `*` crosses `/`. Counted on this tree: 564 of 5,976 tracked files match; dropping those two globs leaves 225 (the audit counted 533 of 5,723 on its tree). `core` is the pin itself, so a pin bump may go through `meta/`, and `registries/*` takes every registry file and `engine_facts/*`, which feed the DLL's generated tables. After the drop, no remaining meta glob matches more under `fnmatch` than under a segment-wise match (checked: both give 225), so the segment half of P3 is already closed by the removal on the Napoleon side. The core's `policy.allowed` itself is warscape-core W23's.
3. **P4 is already live, not "after the 0.16 pin bump".** `core/proxy/tools/build_id.py` `INPUTS` at v0.10.0 already holds `fetch_ui` and `ui_pins` (J30 merged at v0.10.0; `object_ids` prints `viewer/pins.json` as the `ui_pins` input). `wsc.toml` `[ci.inputs] proxy` (line 90) is `^\.github/workflows/|^proxy/(?!runs/)|^core$|^registries/(engine_sites|config_keys)\.jsonl$`: a change to `viewer/pins.json` rebuilds the DLL's id, fires rule 79 and does not run the CI `proxy` job. The `viewer` set matches the file (`^viewer/(?!runs/)`) but that job does not build the DLL.
4. **Hook-module debts** (CONSUMING.md: use the core's API, never re-implement it): `usage_state` reads `registries/jobs/*.json` by glob (`tools/jobs_hooks.py:105-109`); `show` (217-231) re-implements `policy.show`'s plain `git show` half; `PROMOTIONS` (47-55) says "no row yet" for `discovery/core`, `upscale/core` and `viewer/core`, though J64 (the discovery switch) and J63 (upscale and viewer promotion) exist.
5. **Tests**: `tests/test_jobs_hooks.py:303` (`test_main_passes_the_merge_bases_pin_diff`) asserts a source line of the hook instead of behaviour. The legacy-set freeze tests (`LegacyData` in `tests/test_jobs_hooks.py:311` and :318, and `test_the_legacy_set_is_every_brief_on_main_at_j11s_base` in `tests/test_discovery_gate.py:376`) `skipTest` when the base commit (`39eab5e`, `c674fb1`) is not in the clone, which is the case in a depth-1 clone, so they prove nothing there.

## Decisions already made
- **Rule 79 runs for every branch kind, including the empty kind**, because the hook already runs for all of them and `acceptance_problems` is the one authority on what needs passes. Lazy cost: in `policy_problems`, return `[]` first when `facts['acceptance']` is absent and `not (any(rule79_path(p) for p in changed) or 'core' in changed)`, so `plan/` and `brief/` pull requests do not pay for `dll_build_id` and git reads. This is equal in effect to calling it always, because `acceptance_problems` returns `[]` for exactly that input; a test pins the equivalence. A recorded `facts['acceptance']` (the tests, the J62 replay) is still used as given.
- **Ledger lines are per branch** (`branch` must equal the pull request's branch), so a `meta/x` branch that touches `proxy/` needs 20 passes recorded for `meta/x`. That is intended; do not special-case any kind.
- **Meta globs after the change:** drop exactly `"core"` and `"registries/*"`. `"registries/jobs/*"` stays (it is in `plan` and `meta` already, and is a single level). Nothing else is added or removed. The segment matching of P3 is done by a test, not by a hook-side matcher: a new matcher in the hook would be a second matcher next to the core's, which W23 will fix. The test asserts that for every glob in `[policy] plan` and `meta`, the tracked files it matches under `fnmatchcase` equal those under a segment-wise matcher (`*` and `?` within one path segment, `**` for zero or more whole segments, defined in the test in a few lines). It is red today only if a listed glob over-matches; after the drop it must hold, and it keeps future globs honest. Also assert with the core's own `policy.allowed` that `core` and `registries/engine_sites.jsonl` are not allowed for `meta`, and `registries/jobs/J73.json` is.
- **P4 fix = the regex gains `|^viewer/pins\.json$`** (one extra alternative, in `wsc.toml` `[ci.inputs] proxy`), not a derived string: `wsc.toml` is data the core reads, and the test is the derivation. The pins path is `layout.ui_pins` (`[proxy] ui_pins` in `wsc.toml`, else `viewer/pins.json`); the test reads the build id's paths, so a moved pins file fails it rather than being silently missed.
- **The derived-inputs test** (put it in `tests/test_proxy_host.py` beside the classify cases, or in `tests/test_jobs_hooks.py`; pick the one that already imports `ci`): `build_id.object_ids(ROOT, 'HEAD')` gives each DLL input; for each, a path starting `core/` is covered when `ci.classify(['core'])['proxy']` is true (the pin is one file, `^core$`); any other path is covered when `ci.classify([path])['proxy']` is true, and for a folder (`proxy/napoleon`) also `ci.classify([path + '/probe'])['proxy']`. Fail naming the role and path. It reads the INPUTS of the core that is checked out, so it is correct at v0.10.0, v0.22.0 and later. Verify red first (it must name `ui_pins viewer/pins.json` against today's regex).
