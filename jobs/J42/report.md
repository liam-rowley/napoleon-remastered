# J42 report: CI reliability: no red check a branch did not cause

Branch `job/J42`, pull request #57 (opened by the builder for proofs c and d; not for merge until the independent review). The proof
runs are on code commit **`97358f5`**; one later commit, `78edb4f`, changes comments and docs only (`git diff 97358f5..78edb4f`: the
start-up wording in `watcher.ps1`, `Test-Integration.ps1`, `harness/README.md`, `tools/ci_failures.py` and the generated table). Times
were measured on the PC (Git Bash, Docker Desktop) or read from the runs named.

## What exists

1. **The failure table**, `docs/CI_FAILURES.md`, generated by `tools/ci_failures.py` from the GitHub API with its classes in code
   (`CLASSES`), so a new failure is classed in the script, never in the generated file. It covers every failed `gates.yml` run attempt
   from 2026-10-29 00:00 UTC to the job's start (22:20 UTC): **53 failed jobs**, including the ones `gh run list` hides (a failed job
   inside a run the next push cancelled, PR #55's `core_pin` runs among them). Each row has the run id, event, branch, commit, job,
   step, the most telling error line of the log, its class, the guard, and whether the same commit passed that job in another run.
2. **One run per commit.** `gates.yml` runs on `push` and `workflow_dispatch` only; `policy` moved to `.github/workflows/policy.yml`
   on `pull_request` (it needs the pull request's base and head, and runs in seconds). Checks attach to the commit, so the pull request
   shows `gates`, `proxy` and `harness-windows` from the push run and `policy` from its own run, and `gh pr merge --auto` is unchanged.
   A newer push cancels an older run on the same branch, never on `main` (`cancel-in-progress` is now conditional).
3. **A red check is told, not polled for.** `tools/ci_notify.py`, run by a final `notify` job in both workflows (`if: failure()`, the
   only job with `pull-requests: write`), comments once per run attempt on the branch's open pull request: each failed job and step,
   the run URL, and the table class to check first with the local command that reproduces it. `wsc jobs next|review|view` print open
   pull requests with failed checks first (one `gh pr list --json ...statusCheckRollup` call; `--offline` skips it; a failed `gh` is one
   line, never an exception). `wsc jobs next` also names the local `policy` route.
4. **Harness races, fixed at the race, each with a unit guard** (`harness/tests/Test-Unit.ps1`, `static: ...` cases):
   - *Watcher start ("a fresh watcher heartbeat" timeouts, 7 table rows).* Not a housekeeping race. On fresh runners a new watcher
     process reaches its main loop **17 to 35 s** after it starts (`watcher up after N ms`, 20 runs on `66d0fd9` and 20 on `97358f5`;
     39.9 s in run 40970029940, which is what the failing 40 s wait saw), while a warm load of the same script in the unit suite takes
     under 3 s and the `Add-Type` compile under 2 s: the time is powershell.exe start-up before the first statement. The watcher now
     logs its first-statement and compile times, writes its first heartbeat before its first housekeeping pass, and logs that pass's
     duration; `Start-TestWatcher` waits for the main loop with its own budget (150 s) and only then starts the 40 s heartbeat budget.
     A failed start or case prints the watcher log tail, heartbeat age and processes (`Show-WatcherState`), which is how this was found.
   - *`auto-restore` "Cannot find path dxvk.conf".* `Hashes` did `Test-Path` then hash; the watcher deleted the file in between.
     `Hash-OrAbsent` reads each file once.
   - *Repeated cases matched their previous run's log line* (`update rollback 1` run 2 "passed" in 4 s and run 3 saw a half-reverted
     file: dispatch 40968854173 on `97e70cc`). Every integration wait now reads the log after its own mark; `auto-restore` and the
     update cases are repeat-safe; a unit guard refuses any `(Get-Log) -match` in `Test-Integration.ps1`.
5. **Local parity.**
   - `proxy/tools/build.sh --docker smoke` runs the wine smoke test in the pinned container plus CI's wine packages (**70 s**);
     `tests/test_proxy_host.py` runs it after `all` on the same route (native `smoke` needs wine on PATH; otherwise it prints
     "CI-only, warned"). Unit tests for the route (`Route.test_smoke_follows_the_route`).
   - `tests/test_harness_host.py` runs `Run-HostTests.ps1 -Suite unit` under Windows PowerShell 5.1 when a harness input changed
     (**17 s**); no `powershell.exe` fails closed with the fix; `WSP_HARNESS_TESTS=skip` skips with a warning. The integration suite
     stays CI-only and the test says so (see Deviations). Route unit tests with the probes injected.
   - `tools/changed_inputs.py`: `proxy/runs/` is no longer a proxy input (`InputSet.test_pc_run_evidence_is_not_a_proxy_input`). CI
     output change: a diff that touches only `proxy/runs/` no longer runs the `proxy` job; nothing else changes.
6. Docs: `harness/README.md` Tests, `proxy/README.md` Build, `docs/REVIEW.md` (step 1 and Merging), the `gates.yml` header.
   `CLAUDE.md` unchanged (no rule for every session changed). New tools registered: `tools.ci_failures`, `tools.ci_notify`.

## Deviations from the brief, and why

- **The harness integration suite is not run by the local gates.** It sets the machine's time zone, kills `Fake*.exe` and takes about
  6 min on the runner, over what the `tests` gate's 600 s leaves after the proxy route (the brief's kill criterion for this case). The
  local route runs the unit suite and prints that the integration cases are CI-only; one case runs through the dispatch route.
- **"One run per commit" is one `gates.yml` run plus a small `policy.yml` run** on pull requests: `policy` needs the pull request and
  cannot run from a push event without inventing the base. The slow jobs run once.
- **One wait raised, alongside the race:** the watcher start wait went from 40 s to a 150 s main-loop wait plus the original 40 s
  heartbeat wait, because the measured start is 17 to 35 s (above). No other timeout changed.
- **A comment-only commit after the proof** (`78edb4f`): the first wording blamed the `Add-Type` compile, then "the first statement";
  the unit suite's warm load showed both wrong, so the comments now say what was measured. Behaviour is unchanged; its push run is the
  reviewer's to read.
- **The builder opened PR #57** (no auto-merge) because proofs c and d need an open pull request on the job branch; its `policy`
  failure is the expected one.
- **No warscape-core PR.** The `core_pin` rows are fixed by the J41 review's tag fetch; the core's `pin_problems` reading a shallow
  submodule's missing tag as "untagged" is filed below rather than opened now (budget).
- The `-Repeat 20` update dispatch selects `update: a good kit|update rollback 1` only: rollback 2 at 20 repeats would exceed the
  step's 18 min.
