# J99: Vanilla UI reference gallery

Phase 5, foundation (`docs/plans/UI_PIPELINE.md` section 2.2, D55). Liam builds the component library by looking at vanilla and iterating,
not from scratch: "To build the component library I need to see vanilla screens and iterate over them. I can't come up with components from
scratch." This job makes vanilla visible on one private review page: every vanilla screen, and every reusable vanilla component kind with its
states, its usage and the screens it is in, beside the Engraved Plate library's twin (J34) or marked as a gap. J69's sittings with Liam start
from this page. No library or token change (J69), no new design, no in-game RmlUi, no DLL input change.

Model: Opus, reason: D52 (Opus for builds; Sonnet for its reviews).
Budget about 250 tool calls; at the cap, stop, commit, report what is left. Subagents only for independent read-only work. Waiting belongs to
the harness: one background call per sitting or long render, never repeated polling.

## Decisions already made for this job
- **Where things live.** `uikit/napoleon/vanilla/`: `inventory.py` (writes `components.json`), `gallery.py` (composites and the page),
  their tests in `tests/`, committed `components.json` and a `README.md` saying how to rebuild and publish. Tools rows and headers for each
  tool (`tools` gate). No `core/` folder (rule 76); name the core candidates in the report (the compositor is game-agnostic given an atlas).
- **Data rule (J7).** Committed files carry ids, keys, sizes and counts, never loc text or decoded db values. The page and up to ten sample
  images in `uikit/napoleon/runs/<YYYYMMDD>_j99/` may show real strings (as J33's previews did). Composites and shots go to the page, not
  to git: they are regenerated by `gallery.py`.
- **Component inventory (`components.json`, deterministic, `--check` in the tests).** One entry per reusable vanilla kind: every template the
  atlas names in `templates_used` (by script and by uied.templates record), every 9-slice frame group, and the button art families the
  `assets` registry gives the `button_state` role. Per entry: kind, vanilla size or sizes, states with their `assets` ids, use count, the
  `ui_elements` ids using it, and `library`: the J34 class it maps to, or `gap`, with `"uncertain": true` where the match is a guess. The
  mapping is a proposal for J69. Order by use count; on today's atlas the top is vslider and its handle, list, heading, checkbox,
  listview, list header, dropdown menu, sortable list, textview, campaign character card, button group, tab, slider, close button, text
  input and tab group (`template.list`, `template.list_header`, `template.button_close`, ... rows exist for the scripted ones).
- **Screens: static composites of all 300 surfaces** (174 layouts, 126 uied.templates records) at their layout base size, 1x, from the atlas:
  each component visible in its default state drawn with that state's art at its rect, 9-slice frame groups stretched by their insets,
  tiling or stretching as the component flags decode, text from the English loc in the component's font and size with the vanilla `.cuf`
  glyphs (a stand-in face only where a glyph cannot be drawn, labelled on the page). Fields the atlas marks dynamic or parameter show their
  key in a distinct colour. Hidden-by-default components are not drawn; an overlay toggle outlines them. Unresolved art (UI-editor paths)
  is a hatched box with its label. These are references: do not chase pixel parity with the game; the live shots are the truth where they exist.
- **Live shots** for the 44 units reached in run `20261102_j10pc`. First check the PC: if the J10 shots still exist and their sha256 match
  `shots.json`, reuse them and skip the sitting. Otherwise re-run only the J10 drivers' safe states (the same probes, no new routes, no clicks)
  headless at 1920x1080 through `job.sh` and the watcher, on the installed acceptance kit. Probes stay in the run folder (as J9 and J10), so no
  DLL input changes and rule 79 does not apply. Where the live tree gives a unit's rect, also cut a per-unit crop from the shot.
- **Library twins.** For each mapped kind, render the library class in each of its states with `viewer/core/render.py` from one small
  screen (`viewer/napoleon/vanilla_ref/`, `library: true`) at 1080p x 100 %, plus the default faction. PNGs for the page; `gap` kinds show
  "no library component yet". No new library classes, no token edits.
- **The page.** One private artifact titled "Vanilla UI reference" (plain HTML, the `artifact-design` skill), published from the PC session.
  Two views. *Screens*: filters by context, kind (layout or template) and reach (live or static); each card shows the composite, the live
  shot if any, the unit id, component and interaction counts and a link to its component kinds. *Components*: per kind the vanilla state
  strip at 1x and 2x (2x from the J36/J51 masters where they exist, labelled), use count, screens, and the library twin's states beside it.
  JPEG or PNG only (the artifact refuses `.tga`); keep each publish under 64 MB and split across publishes to the same URL if needed. Liam
  comments on the page; acting on comments is J69's, not this job's.
- **Determinism.** A re-run gives byte-identical `components.json` and identical composite sha256 (tested on two surfaces).

## Order of work
1. `inventory.py` and `components.json` from the atlas alone, with tests (counts agree with `discovery/ui/summary.json`).
2. `gallery.py` on five surfaces first: `campaign.entity_lists`, `campaign.objectives_screens`, `common.unit_information`,
   `battle.land_battle_orders` and `frontend.single_player`. Compare each with its live shot where one exists, fix the decode until they read
   right, then run all 300 and record how many drew with no hatched box.
3. Live shots: reuse or one sitting (above). Record every shot's state, sha256 and units in `harness/runs/<YYYYMMDD>_j99pc/README.md`.
4. Library twins.
5. Build the page, publish it, open it, and check ten composites against their shots by eye; put the numbers in the report.

## PC test
Rebuild `components.json` twice: identical. Composite `campaign.entity_lists` twice: identical sha256. If a sitting ran: `job.sh status`
shows no lock and the game not running, `pc_deploy.py status` is clean and the exe is vanilla.

## Kill criteria
- After about 40 tool calls on order-of-work step 2 the compositor still cannot draw a recognisable `campaign.entity_lists`: stop compositing,
  ship the live shots plus the component state strips only, and report what the decode lacks.
- A live state crashes the game or does not reach in 2 attempts: drop it (static only); never add a route that clicks or opens a destructive
  popup.
- The artifact refuses the page 3 times for a cause you did not introduce: stop, stage the site under your PC scratch folder, report the error.
- At about 220 tool calls the page is not published: publish what exists (screens or components, whichever is further), list the rest.
